# AGENTS.md

이 파일은 이 저장소에서 일하는 AI 코딩 에이전트(Claude Code, Codex, Cursor 등)를 위한 온보딩 문서다. 작업 전에 반드시 읽는다.

## 프로젝트 개요

희망환급: 청년 근로자가 소득·카드 내역을 넣으면 연말정산 예상 환급액을 계산하고, 절세 방법을 비교·안내받는 웹 서비스의 **화면(React)** 저장소다.

- 이 저장소는 back(Spring Boot) API와 **JSON으로만** 통신한다. DB나 계산 서버에 직접 접속하지 않는다.
- 이 저장소의 관심사: 화면 흐름, back API 요청·응답, 화면 표시
- 범위 밖: 결제 · 카드 내역 직접 입력(파일 업로드만) · 실명 수집

## 명령어

패키지 매니저는 **npm**만 사용한다. Node.js 22 이상.

```bash
npm install       # 의존성 설치
npm run dev       # 개발 서버 (http://localhost:5173)
npm run build     # 프로덕션 빌드
npm run lint      # ESLint 검사
npm run lint:fix  # ESLint 자동 수정
npm test          # 테스트 (vitest run)
npm run test:flows  # 껍데기 UI 화면 흐름 검사 (기존)
```

## 기술 스택

Vite + React (JavaScript, JSX). 경로 별칭 `@/*` → `src/*`. TypeScript는 쓰지 않는다.

## 폴더 구조

```text

├── pages/        # auth · tax · dashboard · simulation · chatbot · profile · support · admin
```

## 규칙

- 컴포넌트는 함수형으로 작성한다. 파일 확장자는 컴포넌트 `.jsx`, 일반 유틸/로직 `.js`.
- 기존 라우팅을 임의로 바꾸지 않는다. 기존 화면이 있으면 새 화면을 만들지 말고 기존 화면을 고친다.
- 기존 Sidebar · Topbar 등 공통 레이아웃(`components/layout`)을 재사용하고, 기존 색상 · 폰트 · 버튼 · 입력창 디자인을 유지한다.
- 스타일은 기존 `src/styles/globals.css` 클래스를 쓰고, 새 화면은 같은 폴더에 `*.module.css`(CSS Modules)로 만든다. 인라인 스타일(`style={{...}}`)은 지양한다.
- 이미지는 `<img>` 태그를 쓰고 `alt`를 반드시 작성한다.
- 새 로직(함수)을 만들면 같은 폴더에 `*.test.js` 테스트를 함께 작성한다.
- 금액은 원 단위 정수로 다루고, 화면에 보일 때만 `12,000원` 형식으로 바꾼다.
- 사용자에게 보이는 문구는 한글로 쓴다.
- 코드 모양: 들여쓰기 2칸(JS/JSX · CSS · HTML) · 변수·함수명 camelCase · 컴포넌트명 PascalCase(예: `TaxResultCard`) · 문자열은 작은따옴표 `'` · 주석은 한글

## back API 연동

- back API 호출은 `src/api/`에 모은다. 주소 · 방식 · 주고받는 이름은 **API 명세**(팀 노션 「희망환급 API 공통 규칙」 6번 표)를 그대로 따른다. 명세에 없는 이름을 지어 쓰지 않는다.
- 공통 규칙: 주소는 `/api/복수형명사/...` · 조회 GET / 생성·실행 POST / 한 건 전체 저장 PUT / 삭제 DELETE · JSON 이름 camelCase
- PUT은 보낸 값으로 전체를 덮어쓴다 → GET으로 불러온 값에 고친 칸을 합쳐 **모든 칸**을 보낸다.
- 오류 응답은 항상 `{"error": "코드", "message": "문구"}`다. `error`로 분기하고 `message`를 화면에 띄운다. 서버 연결 실패(응답이 JSON이 아님)는 따로 처리한다.
- 회원번호는 주소·본문에 넣지 않는다. 로그인 정보는 back이 정한다. 개발 중에만 `.env`의 `VITE_DEV_MEMBER_ID`를 `X-Member-Id` 헤더로 보내고, **개발 서버(`import.meta.env.DEV`)에서만** 보낸다.
- back 연동 전 데모 데이터는 실제 데이터와 구분되게 둔다. 구현되지 않은 기능을 실제 연동된 것처럼 보여주지 않는다. 화면에 있다고 실제 연결된 것으로 판단하지 않는다 (UI만 / 데모 데이터 / back 연결 상태를 구분).
- API 명세 · 기능명세서 링크가 로그인 문제로 열리지 않으면 내용을 추측하지 말고, 사용자에게 필요한 부분(복사본 · 캡처)을 요청한다.

## Git

- 기능 개발은 각 담당자의 개인 브랜치에서 진행한다.
- 개발이 완료된 기능은 해당 `feature/기능명` 브랜치에 반영한다.
- `feature/기능명` 브랜치의 기능 구현 및 검증이 완료되면 `develop` 브랜치로 PR하여 통합한다.
- `develop`은 기능 통합 및 최종 검증을 위한 브랜치로 사용한다.
- `main`은 최종 안정 버전만 반영하는 브랜치로 사용한다.
- 공통 브랜치나 다른 담당자의 개인·기능 브랜치에 직접 커밋하지 않는다.
- 커밋은 의미 있는 기능 구현·수정 단위로 한다.
- 커밋 메시지는 종류: `무엇을 했는지` 형식으로 작성하고 설명은 한글로 작성한다.
- `커밋 종류`는 feat, fix, chore, docs, test, refactor, ci 등을 사용한다.
- 사용자 확인 없이 git push, 브랜치 삭제, 강제 푸시(git push -f)를 수행하지 않는다.

## 보안

- `VITE_`로 시작하는 환경변수는 **빌드 결과물에 그대로 들어가 누구나 볼 수 있다.** 비밀번호 · API 키 · 토큰 같은 비밀 값을 화면 코드나 `VITE_` 변수에 넣지 않는다.
- `.env`에는 개발용 주소·값만 두고, `.env.example`에는 이름만 적는다.
- 서버 오류 내용(스택 트레이스 등)을 화면에 그대로 띄우지 않는다. back이 준 `message`만 보여준다.

## 작업 방식

- 처음 맡은 작업이나 큰 변경은 먼저 분석한다: 기존 화면 · 라우팅 · 화면 흐름 · 이미 연결된 API와 안 된 API. 분석 결과를 먼저 보고하고, 이 단계에서는 승인 없이 코드 수정·파일 생성을 하지 않는다.
- 새 파일이 필요하면 파일별 역할과 만드는 이유를 설명하고 승인 후 만든다. 기능 파일과 그 테스트 파일은 함께 적어 한 번에 승인받는다.
- 진행 순서: 요청 확인 → 기능명세서 · API 명세 확인 → 기존 화면 분석 → 화면 흐름 설계 → 필요한 부분만 구현 → 다른 화면 영향 확인 → 테스트 → 문서 갱신
- 수정 후 보고: 목적·결과 · 수정한 파일과 역할 · 바뀐 화면 동작을 짧게 요약한다. 해당될 때만 호출하는 API · 추가 환경변수 · 테스트 결과와 미검증 항목 · 아직 안 된 부분 · 갱신한 문서를 덧붙인다.

## 테스트 기준

- 정상 입력과 예외 입력을 모두 확인한다.
- front ↔ back API 요청·응답을 확인한다: 정상 응답 · 오류 응답(`error` 코드별) · 서버 연결 실패
- 공통 컴포넌트를 고치면 그것을 쓰는 기존 화면이 정상인지 확인한다 (회귀 테스트).
- 테스트하지 않은 항목은 「미검증」으로 적는다. 하지 않은 작업·테스트를 완료했다고 보고하지 않는다.

## 문서 관리

`docs/`에 아래 세 가지로만 기록한다 (예외: 초기 세팅 절차 `docs/setup/`). 다른 문서 분류를 임의로 추가하지 않는다.

- `docs/history.md`: 작업·변경 내역. 작업을 마칠 때마다 기록하고, 최신 작업이 맨 위에 오도록 쌓는다.
- `docs/decisions/`: 주요 결정과 그 이유
- `docs/tasks.md`: 구현 예정 · 진행 중 · 남은 작업

`docs/history.md` 형식:

```markdown
### [YYYY-MM-DD] 작업 요약 제목
- **작업 내용**: 수정한 파일 및 핵심 변경점
- **변경 사유**: 변경 목적 또는 해결한 문제
- **검증 결과**: 실행/테스트한 명령어 및 결과
```

- 여러 브랜치에서 `docs/history.md`를 같이 고쳐 develop에 합칠 때 충돌이 나면, 두 기록을 모두 남기고 날짜순(최신이 위)으로 둔다.

작업을 "끝났다"고 말하기 전에 아래를 실행하고, 모두 통과한 결과를 보여준다.

## 하지 말 것

- 요청받은 기능의 대상 폴더 외에 다른 기능(도메인) 폴더나 공통 폴더를 임의로 수정하지 않는다. 수정이 필요하면 작업 전에 먼저 확인받는다.
- 작업 대상 페이지(`src/pages/` 하위 해당 폴더) 외의 다른 페이지, 공통 컴포넌트(`components/common` · `layout` · `ui`), 라우팅 설정을 승인 없이 수정하지 않는다.
- 요청받지 않은 기능 추가 · 기존 기능 삭제를 하지 않는다. 요청받지 않은 외부 라이브러리를 설치하지 않는다 (필요하면 이유를 말하고 묻는다).
- `.env*` 파일을 읽거나 내용을 출력·커밋하지 않는다.
- 사용자 확인 없이 `git push`, 브랜치 삭제, 강제 푸시(`git push -f`) 금지. 커밋 이력을 지우지 않는다.
- 안 쓰는 import·변수를 남긴 채 커밋하지 않는다.
- 린터 규칙을 끄거나 주석으로 숨기지 않는다. 꼭 필요하면 이유를 말하고 허락을 받는다.
- `node_modules/` · `dist/` 같은 빌드 산출물을 커밋하지 않는다.
- JSX를 TypeScript로 바꾸거나, 디자인 전체 교체 · 라우팅 대규모 변경을 하지 않는다.
- 기존 프로젝트를 새로 재작성하거나, 정상 기능·기존 파일을 임의로 삭제·이동하지 않는다.
